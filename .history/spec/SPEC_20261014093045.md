# SPEC: devsecops-reference-stack

Status: extracted from the code on Oct 11, 2026, after the first build. From
this date the spec leads and the code follows. See `CHANGE-PROTOCOL.md`.

## Purpose

A runnable, local-first implementation of a DevSecOps delivery
pipeline for the following elements: 1) a containerized service deployed to Kubernetes by Terraform and Helm, 2)a Postgres database configured by Ansible, 3) secrets encrypted at rest, and 4) Github actions with promotion gates promotes Terraform changes dev to staging to prod behind
peer review, policy checks, tests, and post-deploy validation.

It exists to make one pipeline visible end to end, so that each decision in
it can be pointed at, defended, and improved.

## Scope

In scope:

- One service, one chart, three environments (dev, staging, prod)
- One Postgres instance with per-environment databases
- A local Kubernetes cluster (kind) and a local Postgres container
- GitHub Actions workflows that would run against a real repository
- Policy as code over rendered manifests and Terraform plans
- Documentation that records why, not only what

Out of scope, by decision:

- Any cloud account, cost, or cloud credential
- A real application; the service is a stand-in
- Multi-cluster, multi-region, or multi-tenant concerns
- Observability tooling deployed in-cluster; monitoring is specified, not run
- Dynamic application security testing

## Constraints

- C1. Runs on a laptop with Docker, kind, kubectl, helm, terraform,
  ansible-core, conftest, and nothing cloud-side.
- C2. No real secret is ever committed. Placeholders are labeled as such.
- C3. Every claim about security posture is enforced by code, not by
  convention: a template guard, a policy rule, or a test.
- C4. The repository must stand on its own for a reader who was not on the
  call: README, ADRs, threat model, review notes.
- C5. Vendored files (the toolkit's CI template) are never edited in place.
- C6. Interview-preparation documents are gitignored; everything else is
  tracked.

## Invariants

These must hold on every commit. `scripts/spec-check.sh` tests the ones
that can be tested mechanically.

- I1. The chart refuses to render with a floating or empty image tag.
- I2. Rendered Deployments run as non-root, drop all capabilities, forbid
  privilege escalation, use a read-only root filesystem, and set memory
  limits.
- I3. No password-shaped value appears inline in a manifest, a values file,
  a tfvars file, or a workflow. Secrets are referenced by name.
- I4. Terraform roots are thin: provider, variables, one module call. All
  resources live in `terraform/modules/app`.
- I5. Promotion is ordered dev, staging, prod; staging and prod run inside a
  GitHub environment, where required reviewers are configured.
- I6. A failed smoke test stops promotion and triggers a rollback.
- I7. Every Ansible task that carries a password sets `no_log: true`.
- I8. The application database role is never a superuser.
- I9. Migrations are recorded in a ledger table and a re-run is a no-op.
- I10. Every action in a workflow this repository authors is pinned by
  commit SHA, not tag; the vendored template already is.
- I11. `yamllint -s .` passes; `conftest` passes on every environment's
  rendered chart.
- I12. Every decision that would be expensive to reverse has an ADR.

## Architecture, in one paragraph

Terraform owns the namespace-level posture (namespace, labels, default-deny
network policy, the database secret) and invokes the Helm chart as a
`helm_release`. The chart owns the workload: Deployment, Service, ConfigMap,
NetworkPolicy egress rules, PodDisruptionBudget, and a test hook. Ansible
owns the database as a running service: settings, roles, grants, extensions,
migrations, backups. GitHub Actions owns the order of operations: lint,
scan, policy, plan on pull request; apply dev, then staging, then prod on
merge, each gated by a smoke test; a nightly drift plan. Secrets are
encrypted with SOPS per environment and decrypted only into a job
environment variable.
