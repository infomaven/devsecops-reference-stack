# Security-audit: validate vulnerabilities of this pipeline using a home-grown tool 

This repository builds a secured delivery pipeline for a simple node.JS service with a PostGres backend. It was written using Claude Code. It contains gates, security policies, tests
and promotion controls. For portability, the pipeline's gates were written by the same process that wrote the target application (the service). However from a security viewpoint, there is nothing to check the infrastructure code and security policies of this pipeline. To mitigate this risk, a second tool I wrote can be used to evaluate the security of the code in this repo (or any other repo provided by the user). The tool is called `security-engineer-toolkit`. It lives in a separate repo, has its own tooling, threat model, and published limits.

This page describes how security-engineer-toolkit can be used to evaluate the security posture of this repo. 

## Why a second repository

An audit is only worth something if it is independent of the thing it
checks. Keeping the auditor in its own repository keeps it honest in three
ways. It is versioned and released on its own schedule. It cannot quietly
be weakened to make this stack pass. And it can be reused on other
codebases without carrying this stack along. The two also cover different
stages of the lifecycle, and each states plainly what it does not do:

| | `security-engineer-toolkit` (auditor) | `devsecops-reference-stack` (audited) |
|---|---|---|
| Lifecycle stage | Pre-production code review | Design, delivery, runtime |
| Framework terms | SSDF PW.7, SAMM Verification | PW.8, PS, SAMM Operations and Design |
| Method | Static, AI-paired reasoning | Policy gates, tests, promotion controls |
| Output | Findings and remediation notes | Enforcement that fails a build |
| States its own gaps in | `FRAMEWORK-ALIGNMENT.md` | `docs/THREAT_MODEL.md`, `docs/REVIEW_NOTES.md` |

## The self-audit, applied to this repository

**1. Provenance sets the review.** This stack came out of one generation
session. The toolkit calls that case **Scenario B**: a single process that
may have introduced something, as opposed to years of risk built up by many
authors. The review is aimed at what generation tends to leave behind. The
steps are in `docs/EXERCISE.md`.

**2. Shared CI.** `.github/workflows/security-scan.yml` is the toolkit's
template, copied unmodified. It runs Gitleaks, Semgrep, Trivy, and a
CycloneDX SBOM, with every action pinned by commit SHA and every scanner
binary checksum-verified. Most of this repository's own actions are still
on version tags rather than commit SHAs. That falls short of the template's
standard (see `docs/REVIEW_NOTES.md` 11). Update the template by re-copying
it from the toolkit, never by editing it here.

**3. A closed finding loop.** Toolkit output lands in `findings/`. Every
finding ends in one of three ways: a fix, a Rego rule in `policy/`, or an
accepted risk recorded in the threat model. A policy rule is the only one of
the three that cannot regress silently.

**4. In-repo conformance.** `spec/` is the standard this repository holds
itself to. `make spec-check` reports which features meet their acceptance
criteria and which are known partials, each tied to `docs/REVIEW_NOTES.md`.
The toolkit checks the code; the spec check checks the code against its own
claims.

**5. A shared test target.** The toolkit ships WebGoat as a practice target.
When it is rendered through this chart, the policy gate rejects it, because
it needs a writable root filesystem. The only way past is a waiver that a
reviewer has to approve.

## Applying it to your own repository

1. From your repository in Claude Code, run `/setup-target .` with the
   toolkit's commands installed. Answer the intake for your stack, risk,
   authorization, and how the code was produced.
2. Run `/security-review` and `/security-sweep <dir>` on your executable
   code.
3. Record each finding using `findings/0000-template.md`, and close it as a
   fix, a policy rule, or an accepted risk.
4. Copy `security-scan.yml` into your CI unmodified. Run the rules in
   `policy/` with `conftest` against your rendered manifests and Terraform
   plans.

## The short version

> I generated this stack with an AI agent, then audited it with the
> open-source toolkit I maintain for exactly that case. The toolkit checks
> code, and it says plainly that it does not cover dynamic testing, release
> integrity, or operations. That is what this stack is. Findings from one
> become policy gates in the other, and the same loop works on any
> repository.

## What this is not

It is not a penetration test, and it is not dynamic application security
testing. The toolkit is static and reasoning-based by design. Audit only
code you own or are authorized to review, and keep practice targets on a
local cluster.
