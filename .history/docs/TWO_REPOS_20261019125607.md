# Two repositories, one argument

One repository builds and runs a secured delivery pipeline. The other
audits code, including code an agent generated. Each covers what the other
says plainly that it does not. The seam between them is the point.

## The division of labor

| | `security-engineer-toolkit` | `devsecops-reference-stack` |
|---|---|---|
| Lifecycle stage | Pre-production code review | Design, delivery, runtime |
| Framework terms | SSDF PW.7, SAMM Verification | PW.8, PS, SAMM Operations and Design |
| Method | Static, AI-paired reasoning | Policy gates, tests, promotion controls |
| Output | Findings and remediation notes | Enforcement that fails a build |
| States its own gaps in | `FRAMEWORK-ALIGNMENT.md` | `docs/THREAT_MODEL.md`, known weaknesses |

## Where they are actually wired together

**1. Provenance.** This stack was produced in a Claude Code session. That
is the case the toolkit calls **Scenario B**: one specific generation
process that may have introduced something, rather than years of
accumulated risk from many authors. The toolkit's workflow applies to this
repository directly, not by analogy. See `docs/EXERCISE.md`.

**2. Shared CI.** `.github/workflows/security-scan.yml` is the toolkit's
template, copied unmodified: Gitleaks, Semgrep, Trivy, and a CycloneDX
SBOM, with every action pinned by commit SHA and every scanner binary
checksum-verified. This repository's own checks were trimmed so the two do
not overlap. Its remaining actions are mostly still on version tags rather
than commit SHAs, which is the standard the template sets and this
repository has not yet met: see `docs/REVIEW_NOTES.md` 11. Update the
template by re-copying from the toolkit, never by editing here.

**3. A closed finding loop.** Toolkit output lands in `findings/`, and
every finding ends in one of three places: a fix, a Rego rule in
`policy/`, or an accepted risk recorded in the threat model. A finding
that becomes a policy rule cannot regress silently, which is the only
durable outcome of the three.

**4. A shared test target.** The toolkit ships WebGoat as a practice
target. Rendered through this chart, it is rejected by the policy gate: it
needs a writable root filesystem, and the chart's defaults refuse. The
only way forward is a waiver a reviewer has to approve. Both repositories
appear in one screen, and the guardrail is shown holding against a
workload that genuinely wanted to break it.

## The spec layer

`spec/` holds the specification this repository answers to: purpose,
constraints, invariants, a feature table with checkable acceptance criteria,
a numbered prompt sequence that rebuilds the repository slice by slice, and
a template for modifying one feature. `make spec-check` tests the mechanical
criteria and reports which features are complete and which are known
partial, each cross-referenced to `docs/REVIEW_NOTES.md`. The spec was
extracted from the code after the first build, which is the same thing one
does with any inherited codebase, and it leads from then on.

## What the pair demonstrates

Build the thing, audit your own output, and publish the limits of both.
The toolkit's framework alignment document naming its own gaps is the
evidence for the habit; this repository is what fills them.

## The short version

> I generated this stack with an AI agent, then audited it with the
> open-source toolkit I maintain for exactly that case. The toolkit
> verifies code, and it says plainly that it does not touch dynamic
> testing, release integrity, or operations. That is what this stack is.
> Findings from one become policy gates in the other.

## What this pair is not

Not a penetration test, and not dynamic application security testing. The
toolkit is static and reasoning-based by design. Nothing here is pointed
at infrastructure that is not mine, and the practice targets stay on a
local cluster.
